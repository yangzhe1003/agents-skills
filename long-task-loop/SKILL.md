# Long Task Loop

把用户已授权的目标执行到可验证的结果。按“读取状态 → 选取目标 → 执行 → 验证 → 保存检查点”的循环推进；尚有可执行工作时，继续调用工具，不用一段未来计划代替执行。

这是执行协议，不是后台守护进程。它不能突破宿主的权限、额度、上下文或运行时限制，也不能自行唤醒已退出的 agent。不要声称已配置自动重启或无人值守调度，除非确实另有运行器且已验证。

## 1. 先拆清需求，再创建任务

需求拆解是创建任务的强制前置条件。先读项目说明与相关代码，检查工作区已有修改，把用户目标整理成需求草案。在本节检查通过前，不创建正式任务清单、STATE.md、执行型子代理任务或循环运行器，也不开始实现；可以进行只读调查并向用户展示拆解草案。

按以下顺序完成拆解：

1. **明确目标与边界。** 写清使用场景、预期行为、交付物、包含和排除的范围、已有授权。区分用户明确要求、代码中确认的事实和暂定假设。
2. **列出可验收需求。** 给每项需求一个编号（R1、R2 等），写清输入或触发条件、预期结果、必要的异常和边界情况。避免只有“完善功能”“优化体验”之类无法判断完成的描述。
3. **形成执行项草案。** 每项注明对应需求编号、明确产物、工作范围、前置依赖、验收条件和实际验证方式。按依赖安排顺序，标明可并行项；每项应足够小，能独立执行和判断是否通过。不能只用“前端 / 后端 / 测试”代替行为拆解。
4. **处理未决问题。** 先从现有文档、代码和上下文查证。普通、可逆且不影响业务含义的实现选择自行决定并说明依据；影响范围、业务行为、数据权限或验收标准的问题必须澄清，不能用默认猜测填满任务清单。无法取得必要回答时，报告需求尚未就绪及最小缺失信息，停在需求阶段。
5. **检查完整性。** 每项需求都有执行项和验收依据；每个执行项都能追溯到需求；依赖没有环或缺失；整体集成验收已覆盖；没有会改变拆解的未决问题。凭据、环境等已知执行条件可以明确列为依赖，不能冒充已经具备。

先向用户展示简洁的需求拆解与执行顺序。需求明确且已有实施授权时，展示后直接进入第 2 节，不额外强制一次人工批准；真正的需求歧义未解决时不能创建执行任务。只需少量工作时保持草案简短，但仍需完成上述检查，不为了凑轮数拆碎任务。

检查通过后记录运行预算：用户给出的时间、费用、轮数优先；未指定时每次运行最多 30 轮。使用项目实际提供的测试、构建、类型检查、集成测试、界面操作或其他证据作为验证方式。

执行中发现需求变化或原拆解有遗漏时，先暂停受影响项，回到本节修订需求、依赖和验收映射，检查通过后才新增或调整任务；不靠循环过程中不断追加临时任务代替前置拆解。

## 2. 保存可恢复状态

第 1 节需求拆解检查通过后，才在目标项目创建 `.agent-tasks/<task-id>/STATE.md`，将需求与任务映射一起保存，使用本 skill 的
[状态模板](assets/STATE.template.md)。`task-id` 使用简短英文短横线名称；若路径已存在，先读内容：同一任务就恢复，不同任务就选新名称，不覆盖旧任务。

将状态路径告诉用户一次。记录绝对项目路径，避免恢复时在错误目录操作。状态文件只保存目标、决定、证据、当前工作和精确的下一步，不保存密码、令牌、完整私有数据或大段日志。记录必要的日志路径即可。

维护一个权威状态文件。宿主 Todo 工具可以展示同一清单，但不能替代磁盘检查点。没有必要额外创建多份计划或记忆文档。不要为了保存进度擅自提交、推送或修改全局配置。

每个任务项可用 `pending / in_progress / passed / blocked`。只有相关验收通过才标为 `passed`；代码写完或子代理自述完成不等于通过。

任务总体状态：

- `running`：本次运行正在推进。
- `completed`：所有必须验收项通过，最终结果已检查。
- `blocked`：缺少当前无法自行取得的输入、授权或外部条件。
- `paused`：用户停止、预算耗尽，或运行时限制使本次无法继续。

## 3. 执行循环

一轮是一个有意义的执行及验证尝试，不是一次工具调用。每轮遵循：

1. **选取下一项。** 选择未完成且依赖已满足的最小可交付目标；标记 `in_progress`。简短记录本轮意图和工作范围。外部有副作用的动作先记录，再执行，以便恢复时核实是否已发生。
2. **执行。** 阅读必要上下文后修改或操作；保留无关的用户修改。已有可靠事实不重复搜集。可以并行委派独立工作，但明确文件归属，避免多个写入者修改同一文件。
3. **验证。** 使用项目真实的检查方式验证本轮目标。保存具体命令或操作、工作目录、退出码或结果，以及证据对应的文件/版本。必要时记录关键错误摘要。耗时命令使用宿主后台任务能力，并持续观察其状态；成功启动不代表执行成功。
4. **更新检查点。** 增加本次及累计轮数，记录修改、验证结果、失败原因、剩余工作和精确的下一步。最近记录保留 5 轮即可；长期关键决定和有效验收证据保留在独立字段。
5. **决定继续。** 验收未全部完成，且预算允许、还有可执行项时立即进入下一轮。失败则诊断并修复，不把“测试未过”作为默认终点。

核心判断：

```text
while 存在未验收工作:
    if 用户要求停止: 保存 paused，结束
    if 本次预算耗尽: 保存 paused，报告剩余工作，结束
    选择依赖已满足的任务项
    if 没有可执行项: 保存 blocked，说明最小缺失条件，结束
    执行一个可验证的增量
    运行与改动匹配的验证
    保存本轮证据和下一步
    if 失败: 根据新证据调整方案
全部必要验收通过后，完成最终检查并报告
```

保持正常进度更新：完成里程碑、发现关键阻塞、改变方案或长命令持续运行时，用一句话说明实际进展。不要每调用一个工具就播报。

## 4. 失败与停滞处理

区分失败类型，避免机械重试：

- **实现或测试失败：** 先读取错误和相关代码，提出可验证的原因，再修复。不要跳过、删除或弱化测试来制造通过。
- **环境或依赖问题：** 确认具体缺失项，在授权范围内采用可逆修复。不能修复就标记对应验收未验证，并继续无依赖的工作。
- **暂时性故障：** 宿主已有自动重试时交给宿主。没有自动重试时，允许至多 2 次有界重试；禁止无限重放同一个命令。
- **拒绝授权或用户取消：** 不换一种工具绕过；保存停止原因。
- **未获得新证据、未消除失败、未完成验收项：** 计为无进展。连续 3 轮无进展时换一个实质性策略，比如缩小复现、检查假设或委派独立诊断。换策略后再连续 3 轮无进展，则将该项标记 `blocked`，继续其他可执行项；全部被阻塞时结束并说明事实。

“又修改了一份文档”或“又执行了同一个失败命令”不算任务进展。

本次轮数预算是退出条件，不是完成标准。耗尽后报告 `paused` 和准确续做方式，不能把它写成 `completed`。用户重新发起续做时可建立新的本次预算，并保留累计轮数和未解决的停滞记录。

## 5. 中断恢复

用户给出状态路径时直接读取。否则仅在当前项目的 `.agent-tasks/` 中查找候选；按明确目标匹配。多个任务同样匹配时不能擅自选择或合并。

恢复时：

1. 核实目标目录、用户最新要求和现有工作区变化；检查原需求拆解与验收映射是否仍然完整有效。旧检查点缺少拆解或需求已变化时，先补齐第 1 节检查，再继续执行。
2. 读取检查点中的待办、决定、未通过验证和下一步；不从头重做已经验收的工作。
3. 检查中断时的 `in_progress` 项，核实文件、进程、后台任务和外部操作的实际结果；不重复启动仍在运行的任务，不盲目重发提交、部署等动作。
4. 判断旧证据是否仍有效。相关代码、配置、依赖或环境改变后，只重跑受影响的验证。之前没有结果的命令视为未验证。
5. 更新状态为 `running`，继续最小未完成项。

上下文压缩不是重新规划整个任务的理由。继续引用磁盘检查点。宿主中止或进程崩溃可能发生在保存前，所以检查点是恢复线索，实际工作区和工具结果才是执行事实。

## 6. 完成标准

只有以下条件均满足，才能标记 `completed`：

- 用户目标及所有必需任务项均已验收。
- 与任务风险相称的最终验证通过；项目已有、直接决定本次需求的集成或端到端检查没有被悄悄省略。
- 检查最终改动或产物，确认交付内容与范围一致。
- 记录实际结果、验证证据和任何非阻塞限制。

验证过一次且之后没有相关改动时复用证据，不重复跑同一套昂贵测试。不论轮数多少，都不得以退出码之外的固定口号或完成标记替代验收证据。

最终答复包括：完成了什么、验证了什么、未完成或未验证的内容，以及检查点的可点击路径。阻塞/暂停时给出用户能直接复用的续做命令，而不是含糊承诺未来自动继续。

## 7. 宿主能力与边界

- 本 skill 默认在当前会话中调用工具持续推进，不主动创建后台调度。
- 用户明确要求用 workflow/工作流作为执行手段时，在支持的宿主调用 `CreateWorkflow`，并加载相应官方说明；将循环、检查和退出条件放入该运行器。不要用普通子代理冒充工作流。
- 用户明确要求定时执行或闲时执行时，才使用对应调度工具；先核实支持情况。不要让自动任务递归创建新的自动任务。
- 用户要求跨进程无人值守时，需要已安装且可验证的外部运行器或宿主恢复机制。先查真实能力再实现；不虚构 CLI 参数或 Stop hook 协议。
- 子代理结果需要主代理结合实际产物及验证证据判断。对同一检查指定唯一执行者，避免每个子代理重复跑全套测试。
- 执行内容必须遵守用户授权和宿主安全边界。“自动做到完”为任务内授权，不等于允许任意删除、发布、付费或向第三方发消息。

现成方案及机制差异参见 [参考方案](references/existing-solutions.md)。

## 调用示例

```text
/long-task-loop 完成订单导出功能，并运行相关测试和构建；在任务范围内持续执行直到验收通过。

/long-task-loop 修复这个项目的类型错误。最多 15 轮，不改业务行为，验证通过后结束。

/long-task-loop 继续 .agent-tasks/order-export/STATE.md 中的任务；先核实中断时的结果，再从未完成项继续。
```
