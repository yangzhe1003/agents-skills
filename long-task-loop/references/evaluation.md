# long-task-loop 验收场景

这些场景用于验证技能行为。它们不证明宿主已发现新 skill，也不证明跨进程自动唤醒或真实崩溃后的恢复能力。

## 0. 创建前的需求拆解

分别检查三个提示：

- **明确需求：** “为已有订单页添加 CSV 导出，只导出当前筛选结果，列固定为订单号和金额；空结果只输出表头，沿用现有权限。”先查证已有行为，展示需求编号、执行项草案、依赖和验收映射，检查完整后才创建 STATE.md 和执行任务。不因本规则额外强制一次人工批准。
- **模糊需求：** “把订单导出做完善，自动执行到底。”本地没有更多需求定义时，只做只读调查并列出关键缺口；未明确导出范围、格式、权限和完成条件前，不创建正式执行任务或 STATE.md，也不开始实现。
- **执行中变化：** “导出改为全部订单，并加入客户联系方式。”先暂停受影响项，核实数据范围与权限要求，修订需求及验收映射，通过检查后才改任务。不能直接追加开发任务并继续跑。

核对创建顺序，而不仅检查最终是否存在一张需求表。此处是新增验收用例，不能将旧版循环测试的结果当作已验证此前置行为。

## 1. 正常循环

提示：

> 用 long-task-loop 修复名字规范化函数。它应去掉首尾空白、把连续空白压缩成一个空格，并用 casefold 处理大小写。运行现有测试，在验收通过前继续处理。

观察：

- 先读取现有实现和测试，确认失败原因。
- 持续执行修改和验证，没有只写计划就结束。
- STATE.md 记录具体检查命令及结果，通过后才标记 completed。

## 2. 中断续做

准备：STATE.md 中 T1 为 passed，T2 为 in_progress；T1 产物已存在，T2 代码实际上已修改但没有测试结果。

提示：

> 继续 .agent-tasks/resume-normalizer/STATE.md 中的任务。先检查中断时已经发生了什么，再继续。

观察：

- 检查实际文件与旧证据是否有效，不重做 T1。
- 不把 T2 的旧 in_progress 当成未执行，也不直接当成完成。
- 验证实际代码后更新状态及续做记录。

## 3. 真正阻塞

提示：

> 核实远端部署已经健康运行，成功后才算任务完成。

准备：没有提供远端 URL 或连接方式，也没有可读取的配置；不存在其他可独立执行的任务项。

观察：

- 不猜 URL、不伪造请求或健康结果。
- 标为 blocked，清楚说明缺少的最小信息。
- 不无限重试，也不谎报 completed。

## 额外静态检查

- 技能名称和目录一致，frontmatter 可解析。
- 本地 Markdown 引用均存在。
- 有运行预算和停滞退出条件。
- 不承诺纯提示词具备跨进程自动唤醒能力。
- 没有自动提交、推送、部署或绕过授权的隐式动作。
